# Vista Platform 4.5.0 — full list of changes

> Released **2026-10-07**. The release summary — highlights, what to do before
> upgrading, what each edition includes, and how to verify the signatures — is in
> [CHANGELOG.md](../../../CHANGELOG.md). This page is the complete, per-change
> record behind it.

4.5.0 is a security-hardening and dependency release. The edge, sign-in and
sessions, authorization and tenant isolation, outbound requests, request sizes
and the chart's defaults were reviewed, and every confirmed, bounded finding was
fixed. Each fix was tested through the real router or handler rather than the
helper alone, and checked by breaking the fixing line to confirm the test goes
red. Where a fix is partial, the entry says what is left.

The release also carries the work that followed the security review: asset
classification coverage (the manufacturer of a MAC from the full IEEE registry,
a Smart device class, classification from a host's DHCP vendor class, and
unknown hosts reclassified as evidence accumulates), lease-fresh matching of
probes on DHCP networks, installers for the sensor and the Linux device agent
that enroll what they install, the sensor as a Windows service, and scheduled
scans set up in plain language. Those entries are under "Added", "Changed" and
"Fixed" below.

The schema upgrade is additive except for one deletion. It turns on row-level
security for one table and for the audit-log partitions (see "Authorization and
tenant isolation"); adds two bookkeeping tables, `oui_vendor_backfill_state` and
`class_floor_sweep_state`, one nullable column on `asset_identifiers`
(`device_confirmed_at`) and two columns on `pcap_upload_jobs`
(`truncated_packet_count`, `snapshot_length`); widens the rule kinds
`classification_rules` accepts to include `oui_vendor` and `dhcp_vendor_class`;
and deletes the per-prefix `oui` classification rules Vista shipped (see
"Classification rules are written against manufacturer names"). It changes no
other table. Because the widened rule-kind constraint is not valid for the 4.4.0
schema, a rollback to 4.4.0 after this upgrade is a restore from your backup, not
a `helm rollback`.

After the upgrade, two background passes run in inventory-service: a vendor
backfill about two minutes after the service starts, and a classification sweep
about five minutes after it starts and every six hours afterwards. See "Every
manufacturer the IEEE registry knows" and "An asset still shown as an unknown
host is reclassified".

## Security

### Sign-in and sessions

- **Changing the sign-in email through the profile endpoint is refused.**
  `PUT /auth/me` let any valid access token rewrite the account's sign-in
  address, and the forgot-password flow would then deliver to the new address, so
  a stolen or borrowed session became a takeover of the account. A request that
  carries a different `email` now answers `403 email_change_not_supported`. No
  screen used it.

- **Sign-in no longer reveals whether an address is registered.** Before the
  password was checked, `POST /auth/methods`, `POST /auth/login`,
  `POST /auth/authenticate` and the platform-admin sign-in each told a caller
  whether an address was unknown, deactivated, single-sign-on only, role-less or
  a platform administrator, and answered unknown addresses measurably faster than
  real ones. A wrong password now gets the same invalid-credentials answer
  whatever the account's state, an unknown address spends the same time
  verifying a password as a real one, and an account's state is disclosed only
  to someone who supplied its right password. `POST /auth/methods` no longer
  returns the organization's id except where single sign-on needs it.

- **The email-first password step honours the per-account rate limit,** as the
  other sign-in routes already did; a locked account now answers as locked
  instead of a server error. The password-reset and forgot-password routes are
  now rate limited as sign-in routes: the limiter's list of them named paths that
  do not exist.

- **Platform-admin sign-in is rate limited per address and per account.** Five
  attempts a minute per account and twice that per address (change it with
  `ADMIN_LOGIN_RATE_LIMIT`), and staff single sign-on's start is limited per
  address. A throttled attempt answers `429` with `Retry-After`, never reaches
  password verification and does not count toward the account's lockout, and an
  address refused for its own rate is not charged to the account, so one noisy
  source cannot spend the real administrator's budget. The counters live in Redis
  and fall back to a per-pod counter if Redis is unavailable; the limiter never
  turns itself off. Not done: five wrong passwords still fit in one window, so
  one source can lock an account once, and a distributed attacker can keep it
  locked. `forgot-password` and `reset-password` on the admin console are not
  throttled by this limiter.

- **Resetting a platform administrator's password ends all of that
  administrator's sessions.** Setting a password, deactivating and deleting a
  platform user now do the same, and a failed revoke on set-password is reported
  as an error instead of passing silently. Platform sign-out now also revokes the
  access token it was given. Not done: an access token issued before a
  set-password, deactivate or delete keeps working until it expires (up to one
  hour), and a tenant user's password reset does not end live access tokens.
 

- **A cross-site page can no longer submit the MCP OAuth consent decision.**
  `POST /oauth/authorize` is refused (`403`) when the browser marks the request
  `Sec-Fetch-Site: cross-site` or its `Origin` is not the host that served it.
  Requests that carry neither header, such as non-browser clients, are
  unaffected.

- **Single sign-on for platform staff is bound to the browser that started it
  and uses PKCE.** The admin console's staff sign-in kept its `state` only in a
  cookie, so nothing tied an attempt to the browser that began it and a state
  could be used more than once. An attacker could finish the provider's flow with
  their own account and send the victim the callback address, signing the
  victim's browser in as the attacker. Starting a sign-in now stores the attempt
  server-side under its `state` together with a hash of a random value, which is
  also set in an HttpOnly, `SameSite=Lax` cookie (`admin_sso_binding`, ten
  minutes, scoped to the callback path). The callback refuses unless the cookie
  matches, before it looks up the provider or exchanges the code, and consumes
  the attempt whether it succeeds or fails. The authorization request sends a
  PKCE `code_challenge` (S256) and the token request the matching
  `code_verifier`, for every provider. The attempt lives in Redis; where
  admin-service runs without Redis it is held in the process, and with several
  replicas an attempt that returns to a different replica is refused rather than
  accepted.


### Authorization and tenant isolation

- **Pending sensor registration keys need `sensors.create`.**
  `GET /sensor-manager/sensors/pending` handed every member of a tenant, a viewer
  included, the registration key of every sensor waiting to enrol, enough to
  enrol a rogue sensor. It now needs the same permission that creates sensors.
  The Pending section of **Discovery → Sensors & Agents** is already hidden for
  anyone the request refuses.

- **Tenant administrators can no longer edit or delete platform-wide alert
  rules.** The rules every tenant sees belong to the platform; the service now
  refuses a tenant-scoped write to a rule that has no owner tenant.

- **The admin console API requires a platform identity.** Five admin-service
  routes were gated only by a valid token; `/admin-service/admin/**` now refuses
  a tenant's token before any handler runs, including a tenant token whose role
  claim says `platform_admin`.

- **The sensor registration settings routes are removed.**
  `GET /sensor-manager/admin/settings` was open to every member of a tenant and
  `PUT` to any holder of `settings.update`, and the `PUT` overwrote a
  process-wide setting that every tenant's key creation and sensor registration
  reads. No screen or client called either, so both routes are gone and answer
  `404`. The limits are fixed at the values they had by default: 50 pending
  sensors, a 60-minute registration-key lifetime and address validation off. The
  API description and generated client no longer list them.

- **`PUT /tenant/ui-config` authorizes on identity, not on a role string.** The
  handler trusted a token whose role claim read `platform_admin`; the route now
  needs a platform identity and the `platform.settings` permission, and a tenant
  token is refused with `403` whatever its role is called. The per-tenant
  `PUT /admin/tenants/{tenantId}/ui-config` of the admin console was already
  gated this way and is unchanged.

- **A tenant role can no longer be given a platform role's name.** Creating
  one named `platform_admin` is refused.

- **Usage metering ignores a caller-chosen tenant.** An `X-Tenant-ID` header or
  `?tenant_id=` on an unauthenticated request could meter usage against any
  tenant; the tenant now comes only from the authenticated session.

- **Row-level security is tested against the application's database role.** On
  a Helm install the services connect as a role that is not a superuser, does not
  bypass row-level security and owns no table. A new test, run against a real
  PostgreSQL, proves a tenant cannot read, update, delete, re-point or insert
  across tenants in 16 sensitive tables, and fails if a tenant table has no policy
  at all.

- **Docker Compose installs now enforce row-level security too.** Compose
  services connected to PostgreSQL as the table owner, which PostgreSQL exempts
  from row-level security, so tenant isolation there rested on per-query
  filtering alone. Every Postgres-backed service now connects as `crypto_app`
  (row-level security applies; it owns nothing) with `BYPASS_DATABASE_URL` as
  `crypto_bypass` for the few annotated cross-tenant paths, as the chart does. A
  one-shot `db-roles` service, in `docker-compose.yml`, the production file and
  the smoke file, gives those roles a login on every `docker compose up`, then
  checks the result and fails if `crypto_app` is a superuser, bypasses
  row-level security or owns a table, or if either role cannot read the tenants
  table. It reuses `POSTGRES_PASSWORD`, so there is no new secret and an existing
  `.env` keeps working. An existing install upgrades in place with
  `docker compose up -d`. `db-roles` exits 0 and stays stopped; `make db-roles`
  runs it by hand. If it exits non-zero, `docker compose logs db-roles` says why:
  when the volume was created from a schema that predates the roles, re-apply the
  current schema, which is idempotent and keeps your data:

  ```bash
  docker compose exec -T postgres psql -U crypto_user -d crypto_inventory \
    -v ON_ERROR_STOP=1 -f /docker-entrypoint-initdb.d/01-schema.sql
  docker compose up -d
  ```

  A `password authentication failed` means `POSTGRES_PASSWORD` in `.env` no
  longer matches the one the volume was created with.

- **Alert score history and audit-log partitions are tenant-isolated.** Row-level
  security is now on `alert_framework_score_snapshots`, the compliance
  score-drop detector's history, which the application role could read across
  tenants, and the detector now reads and writes it inside a tenant-scoped
  transaction. Every `audit.activity_logs` partition has row-level security
  enabled with no policy, so the application role reading a partition by name
  gets nothing and writes nothing; reads through `audit.activity_logs` are
  unchanged, and so are the platform's own bypass paths. A partition created
  later gets the same protection. The schema upgrade enables it on every existing
  partition once, a metadata change that holds a brief lock on each. Tooling that
  reads an `activity_logs_y…` partition directly as the application role must
  read the parent instead, or use the bypass role.

### Platform secrets and session tokens

- **In production, services refuse to start on missing or weak platform
  secrets.** With `ENV=production` (the chart's `appConfig.env` default), a
  service exits at start-up, naming the variable, when `INTERNAL_AUTH_SECRET` or
  `ENCRYPTION_MASTER_KEY` is missing or shorter than 32 bytes (for the services
  the chart gives each), or `JWT_SECRET` is set but shorter than 32 bytes.
  A service that only verifies tokens still starts without `JWT_SECRET` when ES256
  verification keys are configured (`JWT_JWKS_URL` or `JWT_PUBLIC_KEYS`), so
  `jwtSigning.acceptLegacyHmac: false` keeps working; with no `JWT_SECRET` and no
  ES256 source it could verify nothing and refuses. `auth-service` and
  `admin-service`, which issue tokens, always need `JWT_SECRET`. A fallback
  written into a service's own configuration can no longer stand in for an absent
  value. Secrets the chart generates (64 characters) and `openssl rand -hex 32`
  pass. See [Secrets management](../operate/security/secrets-management.md).
 

- **Credential encryption can no longer be off in production.** Building the
  credential cipher with an empty key is an error in production instead of a
  pass-through. Outside production it still works, logs `CREDENTIAL ENCRYPTION IS
  DISABLED`, and the services that store credentials (inventory, integration,
  notification, cluster-sensor, device-interrogation and admin) report
  `"credential_encryption": "enabled"` or `"disabled"` in their `/health`
  payloads.

- **The legacy HS256 session window closes by itself.** `jwtSigning.acceptLegacyHmac`
  now defaults to `auto`. The chart used to inject the legacy shared secret
  (`JWT_SECRET`) into every service that only verifies tokens until an operator
  turned it off by hand, so any one of them could forge a session for any user and
  tenant. With `auto`, a fresh install starts with it removed; an upgrade removes it
  once the signing Secret is older than `jwtSigning.legacyHmacWindowHours`
  (192, a refresh-token lifetime plus a day), and an upgrade that first turns
  ES256 signing on keeps it for that window. The window closes at an upgrade, not
  on a timer. `true` and `false` override `auto`, and `helm install` or
  `helm upgrade` prints which mode was chosen and why. `helm template` and Argo CD
  cannot read the cluster, so they keep the secret; pin the value there. See
  [Secrets management](../operate/security/secrets-management.md).

### Outbound requests and scans

- **Searching treats `%` and `_` as ordinary characters.** The user list's search
  and the external connections' search passed the typed text to a `LIKE` pattern
  unescaped, so a search for `_` or `%` matched every row. Both now match the
  characters literally, and so does a backslash.

### Outbound requests and scans


- **Alert webhooks, incident webhooks and platform-staff single sign-on refuse
  loopback, link-local, metadata and private addresses.** The audit service's
  legacy webhook alert action now uses its own guarded client instead of the one
  that carries the service's mTLS identity; incident webhooks use the guarded
  client and read at most a bounded response; and the staff sign-in's token
  exchange and userinfo request (an `admin_login` provider can only be Google or
  Microsoft) use a public-only client, refuse redirects to another origin, read
  at most 1 MiB and no longer panic on a malformed userinfo URL. A receiver on a
  private address no longer receives these.

- **`fd00:ec2::254`, the EC2 IPv6 metadata address, is refused everywhere.** It
  is a unique-local address, so every private-endpoint opt-in would have allowed
  it. It is now in the never-reachable list with the IPv4 metadata address.
  The Alibaba and Oracle metadata addresses are not yet on that list and remain
  reachable under a private-endpoint opt-in.

- **Scans run by the Platform Sensor no longer reach the cluster's own pod and
  Service ranges.** A tenant's Discover Assets or Active Scan run from the
  platform refuses any address inside `networkPolicy.clusterInternalCIDRs`,
  whatever networks the tenant has registered, both when the scan is created and
  for each host as it runs. Scans run by a tenant's own sensor are unchanged, and
  the rest of private address space stays scannable. The chart default is
  RKE2's `10.42.0.0/16` and `10.43.0.0/16`; set it to your cluster's real ranges.
 

### Edge and network

- **The edge Content-Security-Policy is no longer weaker than the application's
  own.** It replaced the single-page app's stricter policy with `connect-src
  'self' https:` and no `object-src` or `base-uri`. In production it is now
  `connect-src 'self'`, pins `object-src` and `base-uri`, and the legacy
  `X-XSS-Protection` auditor is off. The chart template and the compose gateway
  configuration are regenerated, and a new guard, `make edge-csp-test`, fails if
  the weaker policy returns.

- **The auth tier of the edge rate limit drops from 200 to 50 requests a second
  on average (burst 100) per source address, and the edge limits are now
  configurable** under `edgeRateLimit` in the chart: `api` and `auth` each take an
  `average` and a `burst`, and `ipStrategy.depth` or `ipStrategy.excludedIPs`
  choose which address a request is counted against. Behind a load balancer or a
  proxy hop the connecting address is the proxy, so every client shares one
  bucket until `depth` is set to the number of trusted proxies; the default is 0,
  because a depth longer than the `X-Forwarded-For` list makes Traefik answer 500
  on every rate-limited route. The Docker Compose gateway takes the same auth
  numbers and an optional `RATE_LIMIT_IP_DEPTH`. A values file written for an
  earlier release still renders.

- **The MSP dashboard's WebSocket requires its own origin.** An upgrade request
  whose `Origin` does not name the host that served it, or that carries none, is
  refused. Neither user interface opens this socket.

- **The agent mTLS port serves only sensor and agent routes.** The listener on
  `agentMtls.port` (default 8444) of `sensor-manager` and
  `device-interrogation-service` was handed the service's whole router. Traffic to
  it reaches the pod by TLS passthrough, so no edge deny, rate limit or body limit
  applied, and the handshake accepts any client certificate; a self-signed one
  reached the admin routes, the internal service routes, the tenant API,
  registration and `/health`, with the token or signature as the only remaining
  gate. A route now reaches that port only by being registered through the
  listener's own list, and everything else answers `404` before any middleware
  runs. Sensor-manager serves the eleven sensor calls (heartbeat, discoveries,
  command acknowledgement, discovery-job completion and unit reports, certificate
  rotation, config, health, command poll, webhook config and exports);
  device-interrogation-service serves the five agent calls (jobs, results,
  heartbeat, certificate rotation and host inventory). Sensors and agents need no
  change, and enrolment still happens on the public host. One edge case changes: a
  device agent re-run with `--register` against a saved configuration whose
  `PlatformURL` is already the passthrough address and that still holds its old
  client certificate used to reach `/agents/register` through the listener and now
  gets `404`; register against the public host.

- **Seven HMAC-only routes are no longer published at the edge.** The audit
  service's four ingestion routes (`POST /activity-logs` and
  `POST /job-execution-logs/start`, `/{id}/progress` and `/{id}/complete`) and
  three inventory routes (`POST /assets/auto-approve/agent-host`,
  `POST /keys/cloud` and `POST /discovery/jobs/{id}/import`) are authenticated by
  the internal service signature, but sat outside every internal path prefix, so
  the edge forwarded them to the verifier. The edge now denies them by method and
  exact path on every host, both API versions, with and without a trailing slash,
  in both the chart and the compose gateway; their tenant-facing siblings
  (`GET /activity-logs`, `POST /activity-logs/query`, `GET /keys/cloud`) are not
  affected, and in-cluster callers, which use the service address, are unchanged.
  The repository's route audit now recognises every spelling of a signed-only
  route and fails on any middleware that verifies a service signature without
  being classified.

### Request limits and data handling

- **Anonymous and bulk routes stop reading without limit.** Request bodies are
  capped at 1 MiB on the anonymous sign-in routes of `auth-service` and
  `admin-service`; at 32 MiB on the agent intakes for discoveries and results,
  with at most 10,000 discoveries in one batch; and on `evaluate/multiple`, which
  also takes at most 100 frameworks and runs 8 evaluations at a time. A request
  over a limit is refused.


- **Request logs no longer record query strings.** `auth-service` wrote the
  query twice, through the framework logger and its structured logger, so an
  OAuth authorization `code`, `state` or `id_token` on a callback reached the
  logs. Both now log the path only, as does `admin-service`; the query is
  dropped rather than redacted by name. The log written when a handler panics
  still includes the request line, and other services' request logs are
  unchanged; none hosts an OAuth redirect target.

- **A packet-capture job can only open a file in the tenant's own upload
  directory.** `pcap-processor` accepts an absolute path that, once cleaned and
  with symbolic links resolved, is a regular file inside
  `<PCAP_TEMP_DIR>/<tenant id>/`. Anything else, including another tenant's
  capture, a path that climbs out with `..`, a link out and a FIFO, is refused
  permanently, recorded in the audit log as `path_rejected`, and deletes nothing.
  `sensor-manager` writes uploads to `/tmp/pcap-uploads/<tenant id>/`, and neither
  the chart nor the compose files set `PCAP_TEMP_DIR`, so nothing changes by
  default.

- **Two internal services set HTTP timeouts.** The health and fallback servers of
  `discovery-processor-service` and `resource-tracker-service` now have read,
  write and idle timeouts (5, 10, 15 and 60 seconds, as other services use).

- **A sensor registration key is no longer written to the logs.** The key is
  masked when a sensor registers.

- **Database interrogation redacts through every entry point.** The connection
  variants of the database interrogators skipped the settings redaction the
  registry applies; they no longer do, so no configuration secret reaches stored
  results.

- **Only `http` and `https` addresses are rendered as links from stored data.**
  A catalogue or classification-rule URL with another scheme (`javascript:`,
  for instance) shows as text in both user interfaces.

- **A service that verifies internal requests refuses all of them when started
  without its secret.** device-interrogation-service's verifier admitted every
  request if its secret was empty.

- **Chart guard.** A test now renders the chart with its defaults and fails if
  `agentMtls.enabled` is not `true`.

## Added

- **Every manufacturer the IEEE registry knows is now recognised from a MAC, and
  the sensor no longer does the lookup.** The platform resolves the vendor at
  ingestion from the full IEEE registry (all 24-, 28- and 36-bit blocks, about
  53,000 prefixes) instead of a 500-row table compiled into the sensor, which
  left any manufacturer outside it with no vendor at all. A vendor the device
  itself reported, through an agent, an interrogation, a connector or an import,
  is never overwritten, and the registry's answer replaces one an older sensor
  looked up in its own table. A backfill brings every existing asset up to date
  from its MAC identifiers: it starts about two minutes after inventory-service
  does, works through each organization in batches, records the registry snapshot
  it finished under, and is retried hourly for anything it could not complete. A
  release with a refreshed registry runs it again. Sensors need no upgrade for
  this.

- **A Smart device class** for consumer and office connected devices: TVs and
  streaming players, smart speakers, doorbells, plugs, bulbs and locks, game
  consoles and appliances. Roku, Vizio, Ring, Sonos, Bose, Nintendo, PlayStation,
  Philips Hue, Nest, GE Lighting and Amazon devices are classified from their MAC,
  and Cast receivers and Matter nodes from what they advertise on the LAN. IoT
  device keeps its meaning of the enterprise and building estate: cameras,
  sensors, badge readers and building controls. The learned classifier was
  retrained with the new class; its answers still go to Approvals for review.

- **Classification from a host's DHCP vendor class.** Windows clients, Android
  devices, Cisco access points and HP JetDirect printers are classified from the
  vendor class identifier (DHCP option 60) they send when they ask for a lease.
  Catalog ▸ Classification rules accepts a new `dhcp_vendor_class` rule kind, an
  anchored regular expression over that string, so a platform administrator can
  add rules beside the shipped ones.

## Changed

- **The bundled NATS server is upgraded from 2.10 to 2.14.** The NATS project no
  longer patches 2.10; `datastores.nats.image.tag` is now `2.14-alpine`
  (2.14.7 when built). JetStream streams, durable consumers, their
  acknowledgement state and stored messages are read in place from the existing
  volume. A direct 2.10 to 2.14 start was tested on a platform-shaped workload
  with a durable consumer holding unacknowledged messages, and the stream,
  acknowledgement floor and backlog came through intact; the NATS project documents
  upgrading one minor version at a time, so back up before you upgrade. **Rolling
  the chart back afterwards is not clean:** NATS 2.10 rebuilds the stream index on
  its first start and logs `corrupt state file`, with messages and consumer state
  intact in testing. Snapshot the `nats-data-nats-0` volume first if you need a
  clean rollback. A values file that pins `datastores.nats.image.tag` keeps the
  old server until the pin is removed, and an external NATS is unaffected. See
  [Releases & Versioning](../operate/releases.md) (Upgrading → Bundled NATS
  server). The Docker Compose files, nightly integration job and local
  integration-test script already ran 2.14.

- **The bundled NATS server is probed over HTTP, not by opening its TLS port.**
  The probes were a TCP connection to port 4222, which speaks TLS by default
  (`datastores.nats.tls.enabled`); each probe closed the connection before the
  handshake, so NATS logged `TLS handshake error: EOF` every ten seconds. That line
  came from the probes, not from any client. The StatefulSet now probes
  `/healthz` on the monitoring port (8222, plain HTTP in both modes): a startup
  probe (`js-enabled-only`, every 5 seconds for up to about ten minutes, for a
  large JetStream store to recover), a readiness probe (`js-enabled-only`, every
  5 seconds) and a liveness probe (`js-server-only`, every 10 seconds, so a broken
  stream or consumer can never restart-loop the pod). The `nats` Service had no
  readiness probe and could be routed to before the server was ready; it no longer
  is. The pod template changes, so the NATS pod restarts once on upgrade.

- **The documented signature-verification commands now anchor the signing
  identity.** The `cosign verify --certificate-identity-regexp` values printed by
  `helm install` and published in the install guide and README were `…@.*`, which
  accepts a run of the release workflow from any ref. For Core it is now
  `^https://github\.com/VistaSecurity/VistaPlatform-Core/\.github/workflows/release-core\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+(-[A-Za-z0-9.]+)?$`,
  a release tag only. The commercial line's regexp accepts a release tag or `main`,
  because the 4.4.0 commercial release was run from `main` and carries that
  identity. Verification of every published 4.x release is unchanged; checked
  against the 4.3 and 4.4 images and charts. Core images are now built from a Go
  builder pinned to the exact patch in `go.work`, including when the Docker
  Hardened Image base is used. See [Releases & Versioning](../operate/releases.md).
 

- **The `helm test` pod image is updated** to `curlimages/curl` 8.22.0 (from
  8.10.1). No action needed.

- **Two unused cross-tenant lookups are removed from compliance-engine.** Nothing
  called them.

- **Scheduled scans are set up in plain language, not cron.** Pick every few hours,
  daily, weekly on chosen days, or monthly, at a time in your own time zone, and a
  sentence confirms when it will run; the schedule list reads the same way. A
  custom cron expression remains available and is validated before saving.
  Existing schedules keep running exactly as before.

- **Dashboard posture shows its evidence, not a bare percentage.** A risk-band
  donut distinguishes high, medium, low, assessed-clean and unassessed assets; the
  overview also uses clearer inventory wording and bars for overlapping observed
  external-connection measures.

- **Discovery navigation groups what you deploy separately from what ran.**
  Discovery Jobs now includes the run outcomes and failure messages that were on
  Job Logs. Old Job Logs links redirect there, and the rail makes the section
  hierarchy and activity clearer.

- **An asset still shown as an unknown host is reclassified as evidence
  accumulates, without a reviewer.** A host first seen by ARP and later heard on
  mDNS, or whose vendor arrives in a later frame, is now classified over
  everything the inventory holds about it (its MAC identifiers, the services it
  advertised, its LLDP and CDP capabilities, and a vendor or model from the
  device itself) rather than the latest frame alone. A sweep runs about five
  minutes after inventory-service starts and every six hours afterwards, so
  assets already in the inventory are asked again; each move is recorded in the
  asset's class history and nothing the sweep decides is added to Approvals. A
  class a person declared, or a reviewer rejected, is never touched, only a
  rule's answer is applied (a learned-model answer still goes to Approvals), and
  an asset that already holds a real class is left as it is. Expect the
  unknown-host count to fall after the upgrade.

- **Classification rules are written against manufacturer names, not MAC
  prefixes.** Catalog ▸ Classification rules now carries one `oui_vendor` rule per
  manufacturer whose products are all one kind of thing, resolved through the
  IEEE registry. The 496 per-prefix `oui` rules Vista shipped are retired on
  upgrade; an `oui` rule an administrator edited or added is kept, and, as the
  more specific statement about its MAC, still applies before a vendor rule.
  Prefix rules remain available for administrator overrides.

## Fixed

- **The asset timeline no longer gets an "updated" entry every time an observation
  describes itself differently.** A host that announces two services, or that two
  collectors hear in turn, sends a different description of the sighting each time
  (the capture interface, which mDNS service answered and on which port, whether a
  reflector relayed it, which collectors heard it). Those were stored as the asset's
  metadata, replaced as a whole on every observation, and counted as a change, so one
  quiet host wrote about a hundred entries an hour. They describe the sighting, not
  the asset, and now never earn an entry on their own, as the batch and sensor ids
  never did. They are still stored and still show the latest sighting. Entries
  already written are not removed.

- **Passive QUIC is reported once per flow, not once per packet.** A QUIC
  connection opens with a burst of Initial packets, and the sensor sent every
  decoded one on, so each flow produced about sixteen identical discoveries. QUIC
  now goes through the sensor's connection cache like passive TLS and VPN
  detection: one report per flow per dedup window (`capture.dedupTTLMinutes`,
  default 60 minutes), keyed on the destination, the client address, the QUIC
  version, the server name and the ALPN, and not on the client's ephemeral port.
  `external_connections.observation_count` for QUIC now counts sensor reports, as
  it does for TLS, not packets. Upgrade the sensor to benefit.

- **"Scan anyway" scans the rest of the selection.** When an Active Scan includes
  assets outside your registered networks, the platform asks before anything runs;
  4.4.0's fix resent only the held assets, so the others in the selection were
  never scanned while the page said one asset had started. The refusal now carries
  `pending_asset_ids`, the assets a confirmed resend must carry: the whole request
  normally, because nothing ran, and only the held assets when the platform judged
  an asset after other batches had already gone out, so a dispatched asset is
  never sent twice. The dialog resends exactly that set and says which assets are
  scanned with it. Discover Assets' own "Scan anyway" is unaffected.

- **A device interrogation that spends its whole time limit no longer fails at the
  last step.** The job ran under one five-minute context and every write after
  the device answered (findings, discoveries, the completion mark) used it, so a
  slow device, or a worker shutting down, left the final update to fail with
  `failed to interrogate device: failed to mark job completed: context deadline
  exceeded` and the results unsaved. Those writes, the failure stamp and the
  discovery-job record now run on their own bounded context (two minutes; thirty
  seconds for the failure stamp). Stored job errors are redacted and capped at
  2,000 characters by eliding the middle, so the failing step stays at the head and
  the cause at the tail, and an error with an empty message is named by its type.
 

- **Probes of a device the platform has already confirmed at a DHCP address attach
  to that device.** An SSH, TLS or QUIC probe of an address whose owner a sensor
  confirmed by MAC within the last day now matches that owner instead of waiting
  in Discovery → Observations as "Matches an asset" for a person to link. The
  address is still a lease: it follows the MAC when another device takes it, and a
  probe that carries a different NIC, or arrives past the window, is held for
  review as before. Nothing is back-filled, so an address becomes eligible after
  its device's MAC is next seen there (minutes on a sensored network), and rows
  already waiting in Observations stay until you link or dismiss them.

- **A sensor installed with the install command now actually enrolls.** The Linux
  and Windows installers registered the sensor themselves, with a made-up version
  of 1.0.0, which used up the single-use registration code before the sensor
  could. The sensor then never sent a heartbeat or submitted a discovery, and the
  console showed it at v1.0.0 marked as needing an upgrade. The installers now let
  the sensor enroll itself (its private key never leaves the host), wait until it
  has, and print its ID and real version. A rejected code stops the install with
  instructions instead of leaving a service that retries forever. The Windows
  installer checks for Npcap before it changes anything. **A sensor installed with
  an earlier installer never enrolled and its code is spent:** generate a new
  registration key, run the new installer with it, and delete the old row.
  Re-running the installer with the key that enrolled a host keeps its identity
  and upgrades the binary in place.

- **The sensor now runs as a Windows service.** The Windows installer registered
  `crypto-sensor.exe` as a service, but the sensor never told the Service Control
  Manager it had started, so starting the service failed with error 1053 and
  Windows killed the process. The sensor now reports to the Service Control
  Manager: it shows as Running once it is capturing, and Stop-Service or a system
  shutdown sends its last discoveries before it exits. As a service it logs to
  `data\logs\sensor.log` under the install directory, rotated at 10 MB, and
  writes start and stop events to the Application event log. A restart requested
  from the console now brings the service back up. The installer shows the
  sensor's log when registration fails, and stops and disables the service if the
  registration code was rejected.

- **The Linux device-agent installer preserves a registration key unless the host
  can safely store enrollment.** It installs the agent as a hardened service with
  an owned data directory, and waits until the agent has enrolled. A failed
  enrollment save is fatal, and a manual start checks that its data path is
  writable before it contacts the platform, so the key is not spent on an agent
  that could not keep its certificate. An agent from an earlier release that
  logged `Failed to save certificates to disk` cannot be recovered: delete it in
  the console, generate a new key and install again.

- **Merge proposals now offer "Merge as is", "Review merge" and "Keep separate".**
  The recommended selection is previewed before a one-click merge; conflicts that
  need a field choice always open review, and merge notes are optional because the
  audit records the decision details independently.

- **A sensor's own host report can reconcile its physical NICs without treating
  container bridges as host identity.** A verified installation identity keeps its
  asset match, while a MAC held by another asset opens a reviewable merge
  proposal; virtual interfaces are excluded unless they carry the control-plane
  route.

- **Uploaded captures now report truncation and preserve more observations.** The
  packet-capture job identifies packets cut short by its snapshot length (the
  upload page warns when a capture was truncated, for example by a gateway's
  built-in capture tool), TLS reassembly handles retransmitted and reordered TCP
  segments, every observed host is retained, and QUIC conversations are reported
  once in the same form as live sensor observations. Results are returned to the
  platform over service-mesh mTLS. Captures processed before the upgrade read as
  not truncated.

- **Scan jobs no longer stop being picked up after an upgrade or restart.** The
  platform-owned durable consumer remains when a pod drains, where it used to be
  deleted by the pod that created it, leaving the new pod subscribed to a subject
  nothing delivered to while queued scans waited. The stuck-job sweep also
  recreates a consumer that is missing before it republishes queued work. During
  the upgrade from 4.4.0, whose pods still delete the consumer as they drain, a
  queued scan can wait until that sweep next runs.

- **A queued scan no longer counts as its own concurrent job.** The rate-limit
  check excludes the job being picked up, so an organization at exactly its
  concurrent-job limit no longer has its oldest queued scan failed with "too many
  concurrent jobs" while nothing is running, and Start scan now identifies the
  exhausted limit in its 429 response.
