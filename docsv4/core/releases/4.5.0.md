# Vista Platform 4.5.0 — full list of changes

> Released **2026-10-07**. The release summary — highlights, what to do before
> upgrading, what each edition includes, and how to verify the signatures — is in
> [CHANGELOG.md](../../../CHANGELOG.md). This page is the complete, per-change
> record behind it.

4.5.0 is a security-hardening and dependency release. The edge, sign-in and
sessions, authorization and tenant isolation, outbound requests, request sizes
and the chart's defaults were reviewed, and every confirmed, bounded finding was
fixed. Each fix was tested
through the real router or handler rather than the helper alone, and checked by
breaking the fixing line to confirm the test goes red. Where a fix is partial,
the entry says what is left.

The upgrade changes no database schema.

## Security

### Sign-in and sessions

- **Changing the sign-in email through the profile endpoint is refused.**
  `PUT /auth/me` let any valid access token rewrite the account's sign-in
  address, and the forgot-password flow would then deliver to the new address, so
  a stolen or borrowed session became a takeover of the account. A request that
  carries a different `email` now answers `403 email_change_not_supported`. No
  screen used it.

- **Sign-in no longer reveals whether an address is registered.** Before the
  password was checked, `POST /auth/methods`, `POST /auth/login`,
  `POST /auth/authenticate` and the platform-admin sign-in each told a caller
  whether an address was unknown, deactivated, single-sign-on only, role-less or
  a platform administrator, and answered unknown addresses measurably faster than
  real ones. A wrong password now gets the same invalid-credentials answer
  whatever the account's state, an unknown address spends the same time
  verifying a password as a real one, and an account's state is disclosed only
  to someone who supplied its right password. `POST /auth/methods` no longer
  returns the organization's id except where single sign-on needs it.

- **The email-first password step honours the per-account rate limit,** as the
  other sign-in routes already did; a locked account now answers as locked
  instead of a server error. The password-reset and forgot-password routes are
  now rate limited as sign-in routes: the limiter's list of them named paths that
  do not exist.

- **Platform-admin sign-in is rate limited per address and per account.** Five
  attempts a minute per account and twice that per address (change it with
  `ADMIN_LOGIN_RATE_LIMIT`), and staff single sign-on's start is limited per
  address. A throttled attempt answers `429` with `Retry-After`, never reaches
  password verification and does not count toward the account's lockout, and an
  address refused for its own rate is not charged to the account, so one noisy
  source cannot spend the real administrator's budget. The counters live in Redis
  and fall back to a per-pod counter if Redis is unavailable; the limiter never
  turns itself off. Not done: five wrong passwords still fit in one window, so
  one source can lock an account once, and a distributed attacker can keep it
  locked. `forgot-password` and `reset-password` on the admin console are not
  throttled by this limiter.

- **Resetting a platform administrator's password ends all of that
  administrator's sessions.** Setting a password, deactivating and deleting a
  platform user now do the same, and a failed revoke on set-password is reported
  as an error instead of passing silently. Platform sign-out now also revokes the
  access token it was given. Not done: an access token issued before a
  set-password, deactivate or delete keeps working until it expires (up to one
  hour), and a tenant user's password reset does not end live access tokens.
 

- **A cross-site page can no longer submit the MCP OAuth consent decision.**
  `POST /oauth/authorize` is refused (`403`) when the browser marks the request
  `Sec-Fetch-Site: cross-site` or its `Origin` is not the host that served it.
  Requests that carry neither header, such as non-browser clients, are
  unaffected.

### Authorization and tenant isolation

- **Pending sensor registration keys need `sensors.create`.**
  `GET /sensor-manager/sensors/pending` handed every member of a tenant, a viewer
  included, the registration key of every sensor waiting to enrol, enough to
  enrol a rogue sensor. It now needs the same permission that creates sensors.
  The Pending section of **Discovery → Sensors & Agents** is already hidden for
  anyone the request refuses.

- **Tenant administrators can no longer edit or delete platform-wide alert
  rules.** The rules every tenant sees belong to the platform; the service now
  refuses a tenant-scoped write to a rule that has no owner tenant.

- **The admin console API requires a platform identity.** Five admin-service
  routes were gated only by a valid token; `/admin-service/admin/**` now refuses
  a tenant's token before any handler runs, including a tenant token whose role
  claim says `platform_admin`.

- **The sensor registration settings routes are removed.**
  `GET /sensor-manager/admin/settings` was open to every member of a tenant and
  `PUT` to any holder of `settings.update`, and the `PUT` overwrote a
  process-wide setting that every tenant's key creation and sensor registration
  reads. No screen or client called either, so both routes are gone and answer
  `404`. The limits are fixed at the values they had by default: 50 pending
  sensors, a 60-minute registration-key lifetime and address validation off. The
  API description and generated client no longer list them.

- **`PUT /tenant/ui-config` authorizes on identity, not on a role string.** The
  handler trusted a token whose role claim read `platform_admin`; the route now
  needs a platform identity and the `platform.settings` permission, and a tenant
  token is refused with `403` whatever its role is called. The per-tenant
  `PUT /admin/tenants/{tenantId}/ui-config` of the admin console was already
  gated this way and is unchanged.

- **A tenant role can no longer be given a platform role's name.** Creating
  one named `platform_admin` is refused.

- **Usage metering ignores a caller-chosen tenant.** An `X-Tenant-ID` header or
  `?tenant_id=` on an unauthenticated request could meter usage against any
  tenant; the tenant now comes only from the authenticated session.

- **Row-level security is tested against the application's database role.** On
  a Helm install the services connect as a role that is not a superuser, does not
  bypass row-level security and owns no table. A new test, run against a real
  PostgreSQL, proves a tenant cannot read, update, delete, re-point or insert
  across tenants in 16 sensitive tables, and fails if a tenant table has no policy
  at all.

- **Searching treats `%` and `_` as ordinary characters.** The user list's search
  and the external connections' search passed the typed text to a `LIKE` pattern
  unescaped, so a search for `_` or `%` matched every row. Both now match the
  characters literally, and so does a backslash.

### Outbound requests and scans


- **Alert webhooks, incident webhooks and platform-staff single sign-on refuse
  loopback, link-local, metadata and private addresses.** The audit service's
  legacy webhook alert action now uses its own guarded client instead of the one
  that carries the service's mTLS identity; incident webhooks use the guarded
  client and read at most a bounded response; and the staff sign-in's token
  exchange and userinfo request (an `admin_login` provider can only be Google or
  Microsoft) use a public-only client, refuse redirects to another origin, read
  at most 1 MiB and no longer panic on a malformed userinfo URL. A receiver on a
  private address no longer receives these.

- **`fd00:ec2::254`, the EC2 IPv6 metadata address, is refused everywhere.** It
  is a unique-local address, so every private-endpoint opt-in would have allowed
  it. It is now in the never-reachable list with the IPv4 metadata address.
  The Alibaba and Oracle metadata addresses are not yet on that list and remain
  reachable under a private-endpoint opt-in.

- **Scans run by the Platform Sensor no longer reach the cluster's own pod and
  Service ranges.** A tenant's Discover Assets or Active Scan run from the
  platform refuses any address inside `networkPolicy.clusterInternalCIDRs`,
  whatever networks the tenant has registered, both when the scan is created and
  for each host as it runs. Scans run by a tenant's own sensor are unchanged, and
  the rest of private address space stays scannable. The chart default is
  RKE2's `10.42.0.0/16` and `10.43.0.0/16`; set it to your cluster's real ranges.
 

### Edge and network

- **The edge Content-Security-Policy is no longer weaker than the application's
  own.** It replaced the single-page app's stricter policy with `connect-src
  'self' https:` and no `object-src` or `base-uri`. In production it is now
  `connect-src 'self'`, pins `object-src` and `base-uri`, and the legacy
  `X-XSS-Protection` auditor is off. The chart template and the compose gateway
  configuration are regenerated, and a new guard, `make edge-csp-test`, fails if
  the weaker policy returns.

- **The auth tier of the edge rate limit drops from 200 to 50 requests a second
  on average (burst 100) per source address, and the edge limits are now
  configurable** under `edgeRateLimit` in the chart: `api` and `auth` each take an
  `average` and a `burst`, and `ipStrategy.depth` or `ipStrategy.excludedIPs`
  choose which address a request is counted against. Behind a load balancer or a
  proxy hop the connecting address is the proxy, so every client shares one
  bucket until `depth` is set to the number of trusted proxies; the default is 0,
  because a depth longer than the `X-Forwarded-For` list makes Traefik answer 500
  on every rate-limited route. The Docker Compose gateway takes the same auth
  numbers and an optional `RATE_LIMIT_IP_DEPTH`. A values file written for an
  earlier release still renders.

- **The MSP dashboard's WebSocket requires its own origin.** An upgrade request
  whose `Origin` does not name the host that served it, or that carries none, is
  refused. Neither user interface opens this socket.

### Request limits and data handling

- **Anonymous and bulk routes stop reading without limit.** Request bodies are
  capped at 1 MiB on the anonymous sign-in routes of `auth-service` and
  `admin-service`; at 32 MiB on the agent intakes for discoveries and results,
  with at most 10,000 discoveries in one batch; and on `evaluate/multiple`, which
  also takes at most 100 frameworks and runs 8 evaluations at a time. A request
  over a limit is refused.


- **Request logs no longer record query strings.** `auth-service` wrote the
  query twice, through the framework logger and its structured logger, so an
  OAuth authorization `code`, `state` or `id_token` on a callback reached the
  logs. Both now log the path only, as does `admin-service`; the query is
  dropped rather than redacted by name. The log written when a handler panics
  still includes the request line, and other services' request logs are
  unchanged; none hosts an OAuth redirect target.

- **A packet-capture job can only open a file in the tenant's own upload
  directory.** `pcap-processor` accepts an absolute path that, once cleaned and
  with symbolic links resolved, is a regular file inside
  `<PCAP_TEMP_DIR>/<tenant id>/`. Anything else, including another tenant's
  capture, a path that climbs out with `..`, a link out and a FIFO, is refused
  permanently, recorded in the audit log as `path_rejected`, and deletes nothing.
  `sensor-manager` writes uploads to `/tmp/pcap-uploads/<tenant id>/`, and neither
  the chart nor the compose files set `PCAP_TEMP_DIR`, so nothing changes by
  default.

- **Two internal services set HTTP timeouts.** The health and fallback servers of
  `discovery-processor-service` and `resource-tracker-service` now have read,
  write and idle timeouts (5, 10, 15 and 60 seconds, as other services use).

- **A sensor registration key is no longer written to the logs.** The key is
  masked when a sensor registers.

- **Database interrogation redacts through every entry point.** The connection
  variants of the database interrogators skipped the settings redaction the
  registry applies; they no longer do, so no configuration secret reaches stored
  results.

- **Only `http` and `https` addresses are rendered as links from stored data.**
  A catalogue or classification-rule URL with another scheme (`javascript:`,
  for instance) shows as text in both user interfaces.

- **A service that verifies internal requests refuses all of them when started
  without its secret.** device-interrogation-service's verifier admitted every
  request if its secret was empty.

- **Chart guard.** A test now renders the chart with its defaults and fails if
  `agentMtls.enabled` is not `true`.

## Changed

- **The bundled NATS server is upgraded from 2.10 to 2.14.** The NATS project no
  longer patches 2.10; `datastores.nats.image.tag` is now `2.14-alpine`
  (2.14.7 when built). JetStream streams, durable consumers, their
  acknowledgement state and stored messages are read in place from the existing
  volume. A direct 2.10 to 2.14 start was tested on a platform-shaped workload
  with a durable consumer holding unacknowledged messages, and the stream,
  acknowledgement floor and backlog came through intact; the NATS project documents
  upgrading one minor version at a time, so back up before you upgrade. **Rolling
  the chart back afterwards is not clean:** NATS 2.10 rebuilds the stream index on
  its first start and logs `corrupt state file`, with messages and consumer state
  intact in testing. Snapshot the `nats-data-nats-0` volume first if you need a
  clean rollback. A values file that pins `datastores.nats.image.tag` keeps the
  old server until the pin is removed, and an external NATS is unaffected. See
  [Releases & Versioning](../operate/releases.md) (Upgrading → Bundled NATS
  server). The Docker Compose files, nightly integration job and local
  integration-test script already ran 2.14.

- **The `helm test` pod image is updated** to `curlimages/curl` 8.22.0 (from
  8.10.1). No action needed.

- **Two unused cross-tenant lookups are removed from compliance-engine.** Nothing
  called them.

## Fixed

- **The asset timeline no longer gets an "updated" entry every time an observation
  describes itself differently.** A host that announces two services, or that two
  collectors hear in turn, sends a different description of the sighting each time
  (the capture interface, which mDNS service answered and on which port, whether a
  reflector relayed it, which collectors heard it). Those were stored as the asset's
  metadata, replaced as a whole on every observation, and counted as a change, so one
  quiet host wrote about a hundred entries an hour. They describe the sighting, not
  the asset, and now never earn an entry on their own, as the batch and sensor ids
  never did. They are still stored and still show the latest sighting. Entries
  already written are not removed.

## Dependencies

- **Go toolchain 1.26.6 to 1.26.8, and the public runtime image `alpine` 3.24.1 to
  3.24.2.** These are bug-fix patch releases (1.26.7 carries `net/http` fixes;
  1.26.8 carries cgo, compiler, runtime and debug fixes). **They fix no Go
  security advisories:** every advisory against Go 1.26 was already fixed in
  1.26.6. The bump is taken for the bug fixes and to stay current.

- **The web server in the `web-ui` and `admin-ui` images is rebuilt.** Caddy
  2.11.4 becomes 2.11.7, built on Go 1.26.8 with newer versions of its
  dependencies (cel-go, now `cel.dev/cel-go`, 0.32.0; OpenTelemetry 1.47.0 and
  `otlploggrpc` 0.23.0; `klauspost/compress` 1.20.1; chi 5.3.2). This clears
  every finding the image scanner reported against the 4.4.0 user-interface
  images: three of Medium severity (GHSA-gcjh-h69q-9w9g, CVE-2026-81871 and
  CVE-2026-81872) and four of Low severity (CVE-2026-81870). `govulncheck` on the
  new binary finds no vulnerability the code calls; the only residual is
  GO-2026-5932 in `golang.org/x/crypto`, which has no upstream fix and is not
  called. gRPC stays at 1.83.2, because 1.84 is affected by GO-2026-6443. The
  runtime image is re-pinned to the 2026-10-05 build of `caddy:2-alpine`. The
  Node builder for these images is now `dhi.io/node:24-alpine3.24-dev`; if you
  build them yourself with `NODE_BUILDER`, use that or an equivalent Node 24
  image.

- **Go modules** are refreshed across every module, including the AWS and Azure
  SDKs, go-redis 9.23, quic-go 0.63 and gopacket 1.7.4, with every dependency at
  one version everywhere. `govulncheck` reports no vulnerability that the code
  calls. It lists one in a module the code requires but does not call,
  GO-2026-5932 in `golang.org/x/crypto`, which has no upstream fix. Major
  versions of the Azure SDK compute, network and storage packages and of
  `stripe-go` are available and not taken.

- **npm packages** are updated to the latest minor and patch releases across the
  workspaces and the user interfaces, with no major-version changes. The
  `source-map-js` and `postcss-selector-parser` advisories are cleared. One
  advisory remains, in `braces` (GHSA-vfj7-8cjw-p6xm): no fixed release exists,
  and it is reached only through Tailwind CSS 3's build-time dependencies, which
  read static paths in this repository and are not in any image or run at
  runtime. It is accepted until Tailwind CSS 4 migrates the user interfaces.
 

- **Redis, PostgreSQL and InfluxDB images are unchanged.** The chart's `redis:7`
  and `postgres:17` lines are current in their supported series. InfluxDB stays on
  2.8: 2.9 migrates API tokens to a hashed form on first start, which cannot be
  undone.
